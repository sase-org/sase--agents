## What was wrong

Two clones each mint bead IDs from their own `next_counter`, so both can allocate the same ID (`sase-ey`) for different beads. Each writes `events/streams/sase-ey.jsonl`; on rebase that's an add/add conflict, and the resolver's union merge produced a stream with **two** `issue_created` events for one ID. `reduce_event_streams` rejected that, `resolve_bead_conflicts` raised, and every sync worker retried into the same error while holding the sync lock — the ~30-minute wedge.

## The fix

**Rust (`sase-core`, `crates/sase_core/src/bead/events.rs`)** — the merge now tracks per-event provenance (base / ours / theirs / both) through the union, detects duplicate creations, and relocates the loser instead of producing an unreducible stream:

- Root collision → the losing branch's whole subtree moves to a caller-supplied free ID as a new stream.
- Child collision (both sides adding `sase-ey.1` under a shared parent) → renumbered in place to the next free sibling, derived from the stream itself.
- Remaps `issue_id`, `parent_id`, dependencies, cascade/forced-descendant IDs, and re-mints every `event_id`.
- Winner is the base creation, else the older `(timestamp, event_id)` — so the result is identical whichever side git calls "ours".
- `merge_bead_event_streams` keeps its signature and still errors on duplicates; the new behavior is opt-in via `merge_bead_event_streams_with_relocation`.

**Python** — `conflict_resolver` allocates relocation IDs from a store-wide `_RelocationIds` (config `next_counter` plus every known stream ID), writes and stages the relocated stream, and reports `relocated duplicate beads: <old> -> <new>` in the resolution message and sync log. The facade falls back to the legacy binding on older wheels.
