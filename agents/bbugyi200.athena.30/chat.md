## The design

**`memory/` should get the same treatment as the SDD store README** — auto-generated from a Python source, embedding a packaged, drift-tracked infographic — but pushed one step further to be **data-driven**, so it *cannot* drift out of sync with the notes it documents.

The new `memory/README.md` will have: the infographic up top → "How Memory Files Are Used" (tiers + frontmatter schema) → an auto-generated **per-note section** (name, type, description, line count, ~tokens, parent) → a **statistics** summary → a `sase memory` command reference. `sase memory init` regenerates it on every run, exactly as it already refreshes `AGENTS.md`.

**The one insight that shaped everything:** `sase memory init` already writes `memory/README.md` (`init_memory/roots.py:141`), and that same render feeds the `sase validate` drift gate via a byte-for-byte comparison. So the render **must be fully deterministic** — stats derived purely from file contents (reusing the existing `src/sase/memory/inventory.py` primitives), stable sort order, **no timestamps**. Otherwise the freshness gate goes permanently red. That's the "reliable" leg of your ask, and it's the backbone of the plan. The infographic itself is a **static committed asset** (init copies + drift-checks it, never regenerates it at runtime) with a `*.prompt.md` sidecar so it stays regenerable — matching the `docs/agent_images.md` house style.
