## Conclusion

**It's a good idea, but three things the plan assumes aren't true today, and a plain link in the Markdown won't work in the PDF.**

1. **The linker doesn't always run when audio runs.** The swarm macro explicitly says audio "does not imply the linker". Even when the linker does run, it runs alongside audio instead of waiting for it.
2. **The PDF is rendered once.** The `research-highlights` hook fires only when `<name>.md` is first added. `bob highlights create` refuses to overwrite a PDF that has already moved into `lib/`, even with `--force`. So the link has to be in the linker's first commit, which means the linker must wait for audio.
3. **The MP3 isn't in the research repo.** It lives in the sase-listen library on the host. The only web copy is the podcast feed, whose URL contains the feed's password token and which deletes episodes after 90 days. That makes it a bad link target.
4. **A relative `.mp3` link is dead in the PDF.** I rendered one with bob's exact pandoc/xelatex settings: the PDF gets a relative link with no base, which Preview-style viewers like Highlights can't open. The 🎧 emoji also comes out as an empty box in the PDF font, while ▶ renders fine.

## Recommended solution

- **Swarm order:** `audio=true` implies the linker, and the order becomes lead → (image and audio in parallel) → linker. In the two real swarms from today, audio finished at the same time as the image, so with an image this adds about no delay. Without one, publication is about 10 minutes later.
- **Audio agent:** renders straight into the report's folder as `<name>_narration.mp3`, using the existing `sase-listen render -o`. It doesn't use `<name>.mp3`, because SASE's auto-generated companion note for that file could take the report's own `<name>.md` path.
- **Linker:** adds one fixed line to the research-query box at the top: `▶ **Listen:** [4-minute narrated brief](<name>_narration.mp3)`. In a test render of a real report, it appears on page 2 directly above "Bottom line", which is where reading starts.
- **`bob highlights create`:** gets a general feature: local audio links become playable. It copies the MP3 next to the PDF before installing the PDF, and rewrites the PDF link to an `obsidian://` link. That link target is configurable, so it can be switched later without code changes.
- **`bob highlights scan`:** moves the MP3 into `lib/` along with its PDF. It waits for the MP3 if the PDF arrives first. The Obsidian reference note gets an inline audio player above the PDF link: press play, then open the PDF.
- **No changes are needed** in sase core, sase-listen, or the hook configuration.

## Requirement changes I made

- **"Listen while reading" becomes "listen first, or instead".** The audio is a 4-minute summary, not the report read aloud. That's why the link sits at the top and shows its length.
- **New requirements:**
  - The MP3 is committed to the research repo next to the report.
  - A failed narration never blocks publication: no MP3 means no listen line, and the report still publishes.
  - Links never contain the feed token or depend on the feed keeping the episode.
  - The reading-queue note gets an inline player.
- **Swarm runs only for now.** Narrating an already-published report puts the MP3 beside it but doesn't edit the report, because its PDF can't be re-rendered.

## Risks

- **A crashed audio agent would block publication.** If the audio agent crashes or is killed (a failed render is fine), the linker waits forever and the report never publishes. The image agent already has this exposure. The fix is a follow-up: a SASE wait mode that releases on any outcome.
- **Repo growth.** A short narration is about 2.3 MB. If a third of swarms use audio, the research repo grows about 70 MB a month (it's 374 MiB now). Git LFS or partial clones are the escape hatch if that becomes a problem.
- **Not yet tested on the Mac.** I couldn't check from apollo that Highlights opens `obsidian://` links and that Obsidian plays the file. Test that first; if the click feels clunky, switch the link target in bob's config.
